# Эксплуатация учебного демо

## Конфигурация

Production: `DATABASE_URL`, при миграции предпочтительно `DATABASE_URL_UNPOOLED`, общий случайный `RATE_LIMIT_SECRET` длиной от 16 символов. Секрет хранится только в окружении Vercel и игнорируемом `.env`. `DATABASE_DRIVER=neon` по умолчанию; `postgres` включает стандартное TCP-соединение. Значения не попадают в `runtimeConfig.public`. Без обязательной конфигурации сервис отвечает 503, локального fallback в production нет.

Для проверки собранного приложения локально задайте окружение внешней тестовой БД и тестовый `RATE_LIMIT_SECRET`, затем выполните:

```sh
npm ci
npm run check
npm run build
npm run db:migrate
npm run db:check
node --env-file=.env scripts/check-runtime.mjs
npx playwright install chromium webkit
npm run test:e2e
```

Playwright требует те же переменные в окружении процесса; production preview сам `.env` не читает. CI задаёт их явно и поднимает изолированный PostgreSQL 16. Не направляйте браузерные тесты и восстановление дампа на рабочую БД. Публичный smoke создаёт ровно одну новую учебную покупку за запуск.

## Выпуск и миграции

1. Дождаться зелёного Quality checks для точного commit. Он включает build, migration/check, HTTP smoke собранного Nitro, Chromium/WebKit и восстановление тестового дампа.
2. Проверить проект `lumi-paywall`, окружение production и текущий deployment для отката. Выполнить только совместимые добавочные миграции: `npm run db:migrate`, затем `npm run db:check`.
3. Создать staged production: `vercel deploy --prod --skip-domain`. Проверить `/api/health` и HTTP smoke с разрешённым доступом к защищённому deployment. Не отключать Deployment Protection для теста.
4. Продвинуть проверенную сборку: `vercel promote <deployment-url>`. Запустить workflow **Verify public deployment** и посмотреть ошибки Vercel после выпуска.
5. При регрессии вернуть предыдущий deployment через `vercel rollback <previous-url>`. Откат приложения не отменяет миграцию. Удаление/переименование колонок делается отдельными этапами после вывода старого кода.

Применённые SQL-файлы не редактируются: новая миграция получает следующий номер `003_...sql`, добавляется в `REQUIRED_MIGRATIONS`, сопровождается тестом обновления. Ledger и checksum защищают от повторного выполнения и незаметной правки истории. Одновременные migration runners сериализуются advisory lock.

## Диагностика

- `GET /api/health`: 200 `status: ok`; 503 означает недоступную/несовместимую БД либо отсутствующую конфигурацию. Endpoint без customer data, его можно подключить к uptime monitor.
- Проверки readiness объединяются в один запрос на инстанс и кешируются на 5 секунд при успехе / 1 секунду при ошибке. Полная схема проверяется раз в 30 секунд, между проверками — `SELECT 1`. Соответственно, outage может обнаружиться с задержкой до 5 секунд, drift схемы — до 30 секунд; отдельный `db:check` при выпуске кеш не использует.
- Ответ содержит `X-Request-Id`. По нему найти ошибку в Vercel Runtime Logs: операция, HTTP-статус, безопасный тип и код. Не запрашивать у пользователя cookie, IndexedDB UUID или строку подключения.
- 429 содержит `Retry-After`; клиент показывает предложение подождать и сохраняет ключ покупки. Лимиты в минуту (global / IP / device): offers 1200 / 180 / 120, purchase 600 / 120 / 30, restore 1200 / 180 / 60. Граница минутного окна допускает краткий двойной burst — это осознанный fixed-window компромисс.
- При росте 503 сначала проверить env, доступ к Neon и `db:check`; не заменять external DB временной локальной. При потере ответа клиент должен повторять прежний `requestId`.

Автоматического внешнего uptime monitor, оповещений дежурному и SLA у учебного демо нет. Подключение платного мониторинга не входит в задание. Workflow проверки опубликованного адреса запускается вручную после выпуска, без передачи Vercel credentials в GitHub.

## Резервное восстановление

CI после реальных покупок делает `pg_dump -Fc`, восстанавливает его в **другую пустую тестовую БД** через `pg_restore --exit-on-error` и сравнивает ненулевое число покупок. Это проверка переносимости схемы/данных, не доказательство настроенных production backups.

Для production сначала проверить доступный retention/PITR своего Neon-плана в консоли. Восстанавливать в новую ветку/БД, запускать `db:check`, сравнивать покупки и ручной restore на изолированном deployment. Только после проверки переключать строку подключения. Исходную БД и deployment сохранять для возврата. Дампы с пользовательскими данными хранить зашифрованными вне Git и CI artifacts. Конкретные RPO/RTO и production restore пока не измерены.
